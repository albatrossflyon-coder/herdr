## 2026-08-21 (TIC 2, later) — OpenCode/Kilo Bun crash: real root cause found, herdr-specific trigger still open

**Confirmed root cause** (via Pi's investigation): both OpenCode and Kilo Code bundle Bun, and Bun's JavaScriptCore JIT emits AVX512 instructions this CPU (Intel Meteor Lake, no AVX512) can't execute, once code tiers up (~2-3s into a session) — real upstream issue `oven-sh/bun#34215`. Crash is `SIGILL`, happens only when the TUI initializes (interactive mode), not in headless/one-shot mode.

**Real fix found and corrected mid-session:** the actual working env var is `BUN_JSC_useJIT=0` (a JavaScriptCore-specific option) — **not** `NODE_OPTIONS=--jitless`, which is a V8/Node.js flag that Pi's first report incorrectly cited as confirmed-working; it does not apply to Bun's JSC engine at all. Confirmed the real fix via the actual `oven-sh/bun#34215` comment thread, not guessed.

**Wrapper scripts installed** (`~/.opencode/bin/opencode` wrapping the renamed `opencode-real` binary, `~/.npm-global/bin/kilo` wrapping the real `@kilocode/cli` bin) that export `BUN_JSC_useJIT=0` before exec-ing the real binary. **Confirmed working standalone** in a plain bash shell — real 8+ second run, exit 0, no crash, well past the crash threshold.

**Root cause of the herdr-specific trigger, found by Pi + Hermes independently:** the wrapper scripts (`~/.opencode/bin/opencode`, `~/.npm-global/bin/kilo`) set `BUN_JSC_useJIT=0` *inside* the wrapper before exec-ing the real binary, so the var never appears in herdr's own pane environment — it's set one process-exec too late to matter for anything herdr itself might read/log, and more importantly this makes herdr's own env the more robust place to guarantee it, independent of which wrapper (if any) PATH resolves to. Both agents converged on the same fix: set `BUN_JSC_useJIT=0` directly in herdr's `apply_pane_launch_env` (`src/pane.rs`), unconditionally for every pane. This is a no-op for non-Bun agents and only affects Bun's own JIT-heavy paths, which barely matters for an interactive CLI.

**Fix applied and fully verified 2026-08-21 (TIC 2):**
- `src/pane.rs` — one line added to `apply_pane_launch_env`: `cmd.env("BUN_JSC_useJIT", "0")`, with a comment citing `oven-sh/bun#34215`.
- `vuln-hunter scan_diff` (deep_review) → **no findings**.
- `cargo test` → **3265/3266 passing** (same pre-existing flaky test as the Goose change above, confirmed unrelated).
- **Live crash-rate verification** (the real test, since the crash was intermittent at <10% before the fix): launched OpenCode through the actual `herdr agent start --kind opencode` path **11 times** and Kilo through `herdr agent start --kind kilo` **9 times**, all against the freshly rebuilt dev binary. **20/20 clean — 0 crashes**, with genuine rendered TUIs confirmed each time (OpenCode 1.18.21, Kilo 7.4.23), not silent failures.

## 2026-08-22 (TIC 1) — claw-code/Crush/Cline agent-kind integration: in progress, real infra gotchas found along the way

**Goal:** add three more native herdr agent kinds (claw-code, charmbracelet/crush, Cline CLI), same pattern as the Goose integration above. Delegated the actual build/wiring work to the herdr roster (Pi=claw-code, Goose=Crush, Hermes=Cline) rather than doing it directly, per Chris's explicit direction to build up the roster's own track record.

**Real infra problems hit and fixed, worth remembering — these cost real time tonight and will recur if not documented:**

1. **`herdr server` started via a one-shot `wsl.exe -e bash -lc "nohup herdr server ... &"` does NOT survive the invocation ending.** `nohup` only blocks the `SIGHUP` signal; it does not detach the process into a new session. When the invoking `bash -lc` script exits, WSL2 can tear down the whole session and everything in its process group receives `Hangup` regardless of `nohup` — confirmed directly in the server log: process started, then `server shutdown initiated` **14 milliseconds later**, all panes exiting with `signal: Some("Hangup")`. This silently killed the server (and all live agents) at least twice tonight, and looked like a WSL2 VM crash/restart at first (misleading — `uptime` showed 0 min once, but the *second* time `uptime` showed a normal 7 min, proving the server death and a VM restart are two separate failure modes that can look identical from the logs alone). **Real fix:** launch with `setsid nohup herdr server > ~/herdr-server.log 2>&1 < /dev/null & disown` — `setsid` creates a genuinely independent session so the server survives the invoking shell exiting. Verified this actually works by checking `herdr status server` from a **separate** subsequent `wsl.exe` invocation after the fix, not just immediately after starting it.

2. **A real WSL2 VM restart (not the above) also happened at least once tonight**, independently, most likely triggered by running 3 concurrent heavy builds simultaneously (`cargo build` x2 + `go build` + `npm install`) against a machine already tight on memory (~2.9GB `vmmemWSL`, ~4.8GB "truly free" system-wide at the time, though Task Manager's "Available" counter — the one that actually matters for real headroom — read closer to 9GB). Real fix going forward: **don't run more than one agent's heavy compile/build phase at a time** — sequence them instead of parallelizing, even though the file-editing/investigation phases are fine to run concurrently.

3. **`core.autocrlf` mismatch between Windows git and WSL2 git on the same NTFS-mounted repo/worktrees produces a false "every file in the repo is modified" `git status` reading**, from *both* environments simultaneously (each sees the other's line-ending convention as a diff). This is NOT real corruption — confirmed twice by checking `git diff --ignore-space-at-eol --stat`, which came back completely empty both times. Don't panic at a mass-modified `git status`; check `--ignore-space-at-eol` before assuming real damage. Setting `core.autocrlf false` in the repo's local config helps for *future* checkouts but does not retroactively fix files already on disk under the old setting — expect the noise to persist on already-checked-out worktrees regardless.

4. **A worktree's `.git` pointer file (`gitdir: <path>`) can only use one path format at a time, and Windows git and WSL2 git disagree on which.** `C:/Repos/herdr/.git/worktrees/<name>` (Windows-style) works from `git.exe` but WSL2's native git treats it as a *relative* path (Linux git has no concept of a `C:` drive letter) and fails with `fatal: not a git repository`. `/mnt/c/Repos/herdr/.git/worktrees/<name>` (WSL2-style) is the reverse — works from WSL2, fails from Windows/PowerShell. Since the actual agent work runs inside WSL2, standardize worktree `.git` files on the **WSL2-style path**, and do diagnostic `git` checks via `wsl.exe -e bash -lc "..."` rather than PowerShell for any worktree under active agent use.

5. **`sudo` cannot be used at all by any herdr-pane agent** — same limitation as the original Goose build gotcha above (`apt-get install zig` hanging), confirmed again tonight trying to `apt install golang-go`: `sudo: interactive authentication is required`, and the pane just hangs/stalls with no way to supply a password. **Always install language toolchains to a user-owned directory** (`~/.local/go`, `~/.local/zig/...`) instead of relying on `apt`/`sudo` — this also has the side benefit of surviving reinstalls more predictably than a system package.

6. **Go and Zig are now permanently installed** at `~/.local/go` and `~/.local/zig/zig-x86_64-linux-0.15.2` respectively, both added to `~/.bashrc` PATH (`# HERDR-INTEGRATION-TOOLS` block) so every future WSL2 shell has them without re-installing. Confirmed both survive a WSL2 VM restart (Zig's install specifically was proven to survive one of tonight's actual restarts).

**Status as of this entry:** claw-code has a real observed-pattern manifest (`src/detect/manifests/claw.toml`) but no Rust wiring yet; Crush has neither a built binary nor wiring (a working cross-compiled Linux binary exists as a fallback at `/mnt/c/Repos/crush/crush-linux`, built from the Windows-side Go toolchain via `GOOS=linux GOARCH=amd64`); Cline needs reinstalling (`npm install -g cline`) since its install didn't survive the restarts, though its manifest may have survived in the `herdr-cline` worktree. **Shipped:** `Agent::Crush` merged into `feature/crush-agent-support`, pushed to fork, remote SHA `973bf56` independently verified via `gh api`. Same pattern as Goose: manifest-driven state detection (`src/detect/manifests/crush.toml` — blocked/working/idle rules matched against Crush's real terminal output), plus the mechanical registry additions in `sidebar.rs`, `sound.rs`, `detect/manifest.rs`, `detect/mod.rs`. **The real process fix, worth keeping permanently — build any `cargo`/Zig/Go project touching `vendor/libghostty-vt` entirely on WSL2's native filesystem, never on `/mnt/c/...`:**

Building `herdr-crush` directly at its Windows-side worktree path (`/mnt/c/Repos/herdr-crush`) failed twice, for two different real reasons, before this was understood:
1. First failure: a stale system `zig` (0.14.1, from `/usr/bin`, ahead of `~/.local/zig/zig-x86_64-linux-0.15.2` in `PATH`) doesn't satisfy `vendor/libghostty-vt`'s `minimum_zig_version = "0.15.2"` — fixed by pinning `ZIG=~/.local/zig/zig-x86_64-linux-0.15.2/zig` as an env var on the build command (herdr's `build.rs` already supports this override; don't fight `PATH` ordering, just set the var).
2. Second failure, after the Zig fix: `error: failed to rename compilation results ... AccessDenied` from Zig's own build cache — a real Windows-Defender-vs-NTFS-rename race that happens specifically when Zig's `.zig-cache` (or Cargo's `target/`) lives on the `/mnt/c` drvfs mount. `CARGO_TARGET_DIR` alone only redirects cargo's own output, not Zig's separate cache dir nested inside `vendor/libghostty-vt` — so the real fix is copying the **whole worktree** (`rsync -a --exclude target --exclude .zig-cache`) to a native WSL2 path (`~/build/<worktree-name>-src`) and building entirely there. Both cargo's target and Zig's cache end up on ext4, and both failure modes disappear. WSL2 stayed at normal memory usage (~1.3GB) through the full native-fs build — confirming the earlier "3 concurrent builds crash WSL2" gotcha was compounding *this* I/O problem, not a wholly separate one; a single build on `/mnt/c` alone was already fragile before concurrency ever entered into it.

**Sequencing note Chris asked to have documented explicitly:** build **one integration at a time**, not three in parallel worktrees simultaneously — this is what caused the original WSL2 `Wsl/Service/E_UNEXPECTED` crash pattern earlier in the night (see the entry above). Whether 2 *native-filesystem* builds could safely run concurrently now that `/mnt/c` I/O is out of the picture, and now that `.wslconfig` was raised to 11GB memory / 16GB swap, is a genuine open question — not yet tested. Verify with a real two-at-once native-fs build before relying on it, rather than assuming the `/mnt/c` fix alone makes concurrency safe.

**Committing/pushing across the Windows/WSL2 boundary:** committing is cheap (small diff, not the heavy I/O culprit) and was done from the original `/mnt/c/Repos/herdr-crush` tracked worktree, not the scratch native-fs copy — confirmed identical via `git diff -w` on both before committing. Pushing over HTTPS from *inside* WSL2 hung indefinitely (no `gh` CLI installed there, no credential helper configured — a `git push` with no way to authenticate and no TTY to prompt on just hangs, same failure class as the `sudo` gotcha). Fix: push the same branch from the **main Windows-side checkout** (`C:\Repos\herdr`) instead — worktrees share one object database, so the branch and its commits are already there; native `git.exe` already had working GitHub credentials from prior sessions. Landing verified via `gh api repos/albatrossflyon-coder/herdr/branches/feature/crush-agent-support --jq '.commit.sha'`, matched `973bf56` exactly.

**Also fixed as a side effect of the CRLF investigation below:** a stray uncommitted line-ending corruption (mixed CRLF/LF within `src/detect/mod.rs` etc., unrelated to tonight's own edits) was normalized back to pure LF before commit — see the `herdr` section of `LEARNINGS.md` for the full diagnostic trail, since it produced a genuinely confusing false signal (`git diff -w` reading as empty) worth understanding before it recurs.
